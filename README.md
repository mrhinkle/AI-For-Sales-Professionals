# AI for Sales Professionals

A training program for sellers, built as a repository so it can be read by a person or by a chatbot. The master curriculum lives in `modules/`, the standard proposal in `program/`, and each client or event gets a fork in `audiences/` that picks modules, swaps in their company, product, CRM and buyer, and builds to a single HTML deck with speaker notes.

The whole program hangs on one rule: **the AI drafts, you send.**

## Build

```
npm install                      # once: marked, js-yaml
node deck/build.mjs              # every audience → deck/dist/<audience>.html + audiences/<audience>/speaker-notes.md
node deck/build.mjs buoyant      # one audience
node scripts/check.mjs buoyant   # lint + headless-Chrome overflow check + PDF; writes deck/dist/buoyant-check.txt
```

The check needs Google Chrome on this Mac (or `CHROME=/path/to/chrome`). It fails the build on an unresolved `{{variable}}` or any slide whose content crosses the 620px floor, and warns on em-dashes, exclamation points, long lists, missing or long speaker notes.

Decks are one self-contained HTML file: arrow keys and space to move, F for fullscreen, N for speaker notes, print to PDF for one slide per page. No network needed.

## How a fork works

```
audiences/
  master/audience.yaml      the full program: defaults for every variable, all eleven modules
  _template/                copied by scripts/fork-audience.mjs
  buoyant/
    audience.yaml           title, date, length (short = 60 min), vars (Buoyant, Linkerd, HubSpot, Apollo), module list with excluded slides
    brief.md                who is in the room, what they sell, what already happened, the live-demo plan
    run-of-show.md          clock, blocks, slide numbers, scope cuts
    overrides/              audience-only modules (a slide tying the session to the inbound plan)
    speaker-notes.md        generated by the build
```

An audience inherits everything from master and states only what differs. Modules are shared, so a fix to `modules/04-outreach.md` reaches every audience on the next build. A fork can exclude slides by id, replace a module with its own file, or add a module of its own. Variables like `{{company}}` and `{{crm}}` fail the build if a fork leaves one unset, so a deck never ships saying "your CRM" to a room that uses HubSpot.

## Program lengths

| Length | Teaching minutes | Shape |
| --- | --- | --- |
| short | 60 | Primer: one rule, where AI fits, the three files, research and outreach by live demo, calls, guardrails, first week |
| half | about 150 | Workshop: everything above with hands-on exercises on real accounts, plus proposals and pipeline in brief |
| full | about 260 | Full day with breaks: every module with exercises, plus a 30-day follow-up call in the proposal |

Each module's front matter carries its minutes for each length; the build prints the total so a run of show can be checked against the booked time.

## Voice and design

Slides and notes are in Mark Hinkle's voice: one person across a table, sentences for titles, contractions, the plain point first and the reassurance second, at most four bullets. Decks build in the **Node** theme, the AIE Network training template: white canvas, Verdana, Inter, JetBrains Mono, one orange, and the brand mark's linked circles as the structure. Tokens, image rules and the pre-ship checklist are in [design.md](design.md). Other explored skins live in `deck/theme/skins/` and `npm run previews` renders them side by side.

A deck needs visual interest beyond type: a photograph or screenshot every four or five slides. The builder takes `photo:` on title, divider and statement slides, markdown images in body slides, an `image` layout for screenshots with or without side text, and a `links` layout. Assets live in `deck/assets/`.
